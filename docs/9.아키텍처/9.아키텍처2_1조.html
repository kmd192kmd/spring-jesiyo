발표용 아키텍처 자료 · Spring 5.3.9 · Spring Security · WebSocket · Redis(Lettuce/Redisson) · Oracle 19c(Cloud Wallet) · Tomcat 9 · MyBatis · STS3 · JUnit4 · Postman · Git/GitHub

① 시스템 전체 구성도

클라이언트(Browser/Postman/Toss SDK) → Tomcat 9 위의 Servlet Filter Chain → DispatcherServlet/Spring Security/WebSocket → Service & MyBatis → Oracle 19c · Redis · 외부 API 흐름을 담았습니다.

② 계층형 구조 + 핵심 시퀀스

9개 도메인(Member, Auction, LiveAuction, Chat, Trade, DirectSale, Payment, Location, Category)을 동일한 4-Tier(Presentation → Service → Persistence → Data/External)로 정리하고, 라이브 경매 입찰 / 채팅 메시지 흐름을 시퀀스로 동시 표시합니다.

④ 발표 시 어필할 포인트

1) "Legacy 4파일" 구조를 정확히 이해하고 있다

  • web.xml — Filter 순서: 인코딩 → HiddenHttpMethod → Spring Security → DispatcherServlet
  • root-context.xml — Hikari/MyBatis/Tx/AOP/메일/Service 빈 (Controller 제외 스캔)
  • servlet-context.xml — DispatcherServlet, ViewResolver, MultipartResolver, /bid-ws WebSocket
  • security-context.xml — form-login, intercept-url, BCrypt, 핸들러

2) 동시성 — 라이브 경매가 가장 화려한 포인트

  • ① Redis 캐시로 최고가 Fail-Fast (DB 안 가고 즉시 거절)
  • ② Redisson tryLock 분산 락 → 동일 경매에 동시 진입 직렬화
  • ③ Critical Section에서 DB 이중 검증 + point_lock 테이블로 예치금 묶기
  • ④ 트랜잭션 성공 후에만 Redis 캐시 갱신 + 종료 시 캐시 삭제

3) 채팅 — Pub/Sub로 멀티서버 확장 대비

  • 같은 서버 세션에만 보내던 구조를 Redis Pub/Sub으로 리팩터링
  • Publisher가 chat 채널에 publish → Subscriber가 받아 ChatRoomSessionManager로 방별 broadcast
  • 채팅 본문은 DB 저장(원본) + Redis 전달용으로 책임 분리
  • AOP로 키워드 매칭 → 추천 상품 푸시 (관심사 분리 사례로 어필 좋음)

4) 보안 / DB 인증

  • Oracle Cloud Wallet(mTLS)로 DB 자체 암호화 연결
  • Spring Security + BCrypt + Custom 핸들러로 세션 통일
  • Hikari 풀 4 + keepalive로 Wallet 환경의 끊김 방지

5) 결제 — 멱등성과 트랜잭션

  • PaymentApi가 주문 생성 시점에 orderId = "PAY-"+seq로 멱등 키 생성
  • 토스 confirm 결과를 받고 updateStatus("DONE") + addPointByOrderId
  • 포인트 지급은 result != 1이면 RuntimeException — 중복 지급 차단

6) 테스트 / 협업

  • spring-test + JUnit4로 DAO 단위테스트
  • REST 검증은 Postman 컬렉션
  • 형상관리: Git/GitHub, 개발 IDE는 STS3
